YunoBall Architecture#

StatMuse, but more advanced — natural-language search over NFL historical data.

Core thesis#

A stats product lives or dies on accuracy. Free-form generation over text will hallucinate numbers. So YunoBall is natural-language → structured query over a curated, authoritative warehouse. A deterministic parser translates, a template builder writes the SQL; the database is the source of truth.

One language, one runtime — TypeScript end to end:

Why these choices#

DecisionRationale
Structured intent, not raw SQLThe parser emits a typed QuerySpec, never SQL → fast, cacheable, and injection-proof: we build the SQL from allowlists.
Numbers from facts, not RAGAnswers are computed from the warehouse, never retrieved from prose.
Express (TypeScript) backendOne language and runtime across the whole app; types shared with the frontend so the contract can't drift.
Plain-SQL schema + idempotent migrateThe warehouse is sixteen tables; CREATE TABLE IF NOT EXISTS beats a migration framework at this size, and column widenings ship as ADD COLUMN IF NOT EXISTS in the same file.
nflverse release CSVsFree, open, comprehensive (stats back to 1999). No scraping/ToS risk, no SDK dependency.
Provider modules under ingest/providersNew sources (ESPN, SportsDataIO, live scoring, injuries...) are independent modules; the public API never changes.
Read-only role for readsEngine-executed SQL and API reads run least-privilege when READONLY_DATABASE_URL is set.

Query pipeline#

The common path is deterministic end to end:

  1. L1 cache — normalized question text. Repeats → instant.
  2. Resolve — fuzzy-match names to a canonical player_id (last-name / typo tolerant; a difflib-equivalent matcher).
  3. Parse to QuerySpec — rule-based, zero-LLM. Twenty-three intents: leaders, player totals (season/career/first-N), single-game marks, comparisons, game logs, ranks, streaks and milestones, scoring, bios, draft picks, team stats, rosters, awards. The spec is a discriminated union on intent, so a field the executor doesn't consume is a compile error rather than a wrong number. Every intent carries a REG/POST scope.
  4. L2 cache — keyed on the spec, so different phrasings that mean the same thing share an answer.
  5. Build → execute — deterministic template with bound params; stat columns come only from an allowlist.
  6. Narrate — templated from spec + rows.
  7. Questions that don't parse get an honest "can't answer that yet" — never a guess.

Every answer records a durable share_id (Postgres answer_cache) powering /a/<share_id> share pages.

Ingestion#

pnpm ingest:nfl --season 2024 (or --all, --years ..., --season-type REG, --dry-run). Idempotent upserts; per-dataset failure isolation; every malformed/orphaned row is skipped with a logged reason and an end-of-run tally. Normalization: stable ids (gsis player ids, nflverse game ids, current-franchise team ids with relocations folded forward), playoff rounds collapsed to POST, postponed games kept with NULL scores. scoring_plays distills play-by-play down to touchdown events only (~1.5k rows/season instead of ~50k), powering first/last-TD questions and the player-page touchdown log without storing full pbp. The same stream also accumulates player_game_advanced (per-player-game EPA, success counts, CPOE) and per-team drive counts, so the pbp files are read once, not three times.

The nflverse stats_player files carry 145 columns; the mapping consumes the special-teams, situational and extended-defensive blocks alongside the original box score, so kicking, punting, returns, first downs, YAC and penalties are all queryable without an extra fetch. Team box scores come from the stats_team release, fetched best-effort — if it is unavailable a team-game row still carries its result, as it always did.

Table relationships:

The rest carry no foreign keys, deliberately: draft_picks and player_id_map reach past the loaded seasons, a stat_facts subject can age out of the warehouse, and query_audit / answer_cache are app tables rather than warehouse ones.

Notable facts#

A scheduled miner (pnpm facts:mine) runs a registry of reviewed SQL probes over the warehouse and stores the rare lines they find in stat_facts, one of which is published per day. Same invariant as the query engine: the SQL is checked in, the headline comes from the probe's own template, and every fact carries the query and peer rows that prove it. A model contributes probe source at design time only — nothing generative runs in a request. Coverage floors are derived from the warehouse so no fact can claim to see further back than the data does. See FACTS.md.

What makes it "more advanced" than StatMuse#

  • Transparency — every answer exposes the exact SQL + source rows.
  • Deep coverage — a full 1999–present warehouse of box scores and rollups.
  • Shareable answer cards and computed-on-the-fly standings/leaderboards.

Testing#

  • apps/server/test/engine.test.ts — parser/builder/narration golden cases, including a check that the similarity port matches CPython's difflib.
  • apps/server/test/battery.test.ts — the 100-question battery: every input must land in a QuerySpec, a tailored refusal, or an honest null. The failure mode it guards is the wrong bucket, not the wrong number.
  • apps/server/test/audit.test.ts — the second-layer auditor's DB-free paths (contradictions, coverage bounds, the Super Bowl played-year rule).
  • apps/server/test/sweep.test.ts — every stat-bearing intent × every stat in the allowlist, EXPLAINed against a schema-only scratch database. buildSql must never emit SQL that fails to plan; a stat an executor can't compute is the parser's job to refuse.
  • apps/server/test/facts.test.ts — miner phrasing, the coverage-floor guard (pinned from three directions), scoring, and the shape of every registered probe's SQL — built and inspected, never executed.
  • apps/server/test/espn.test.ts — headshot resolution: nflverse URL wins, espn_id builds the CDN fallback, unknown players stay null.
  • apps/server/test/ingest.test.ts — messy-data suite (relocations, duplicate ids, postponed games, orphan stats, dry-run, idempotency, schema drift) against a scratch Postgres database.
  • Playwright e2e (apps/web/e2e) over both servers; CI ingests a real season into a service Postgres before running it.
